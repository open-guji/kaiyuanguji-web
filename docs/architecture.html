开源古籍网站架构

kaiyuanguji.com 现在是怎么搭起来的：页面怎么出、数据怎么流、缓存怎么换、搜索和后台放在哪、发布和回滚怎么走、出了事去哪看。

依据 2026-09-29 线上实测（网站 3f5073b，组件库 0.11.1，数据 2871cea）与 kaiyuanguji-web 仓代码。代码与本页冲突时以代码为准，并顺手改本页。

一、全景

整个站是一份代码、两个部署目标。读者访问的是正式站 www.kaiyuanguji.com，每次改动先到测试站 staging.kaiyuanguji.com 验过，再由人或由自动流程提升（promote）到正式站。索引数据不放在页面产物里，由 CI 打包后放进独立的数据桶，浏览器和服务端都从那里取。

先测试站，后正式站push 到 main 先部署测试站并跑全套 e2e；正式站只由 promote 上，上的就是测试站验过的那一版。
代码和数据是两条链页面产物里不带数据。数据在 CI 里打包，放进数据桶；改数据不必重新构建站点。
条目页服务端渲染约 14.7 万个条目页按请求渲染，让搜索引擎看到正文；靠 CDN 缓存和按改动清缓存扛流量。
组件库在另一个仓列表、详情、阅读器在 npm 包 book-index-ui；先发包，再在网站里升版本。

二、为什么这样设计

旧站是 Next.js 静态导出，所有页面在构建时生成，条目页只是一个客户端渲染的空壳。规模和需求变了以后，这条路走不下去。

需求静态导出的问题现在的做法
搜索引擎收录条目条目页的 HTML 里没有正文，十几万条对爬虫是同一个页面云函数按请求渲染条目页，标题、描述、正文摘要、结构化数据都在首屏 HTML 里
条目从 14.7 万增长到约 200 万每页约 10 个文件，14.7 万页就是 147 万个文件、约 7 GB，平台单项目上限 2 万文件不预渲染。函数渲染一页约 20 ms CPU，慢的是取数，用缓存解决
改一条数据不该冲掉全部缓存每次发布换一个全局版本号，所有条目 URL 一起变数据按内容哈希寻址（h1）；发布时只清改动的条目页
发布前要能验证只有一个站，坏了就是线上坏了测试站独立部署、独立 KV、独立数据前缀；正式站按钉住的 commit 发
后台功能（登录、反馈、错误）纯静态站靠边缘函数补，代码和站点各管各全栈项目：页面、云函数、边缘函数在同一个项目里一起发

几条贯穿始终的原则：

  • Git 是内容的唯一真源。网站上的数据全是 Git 的只读发布物，网站不做非数据库不可的事。
  • 服务端只渲染本条目自己的数据。版本列表的书名、人物的作品表这类「别的条目的字段」交给浏览器补，这样「哪些页要清缓存」恰好等于「哪些条目变了」，不用算依赖图。
  • 公众站无状态。有状态的东西（搜索索引、校对平台）放在别处，公众站挂了或重发都不丢东西。
  • 没有一步能静默失败。每个打包、上传、清缓存的步骤都带数量校验，缺一个输入就让构建失败，而不是悄悄降级。

三、页面怎么出来

站上的页面按出法分四类。判断一个页面属于哪类，看它的数据在什么时候取。

类型页面怎么出
静态页/ /about /contact /privacy /roadmap 等说明页构建时生成，随部署发布；内容在网站仓里
构建期索引页/catalog（古籍总目）、/read（阅读首页）打包数据时顺带生成分类树和分页 JSON（current/catalog/、current/read/），页面读这些分片。按四部分类，每页 20 条，不依赖搜索服务
按请求渲染/item/[id]（作品、版本、丛编、人物）云函数按 id 取条目 JSON，渲染首屏 HTML，边缘网络缓存。浏览器里的组件再接手，补全其他条目的信息
客户端页/book-index（检索）、/read/[id]（阅读器）、/admin/*服务端只出外壳，数据由浏览器从数据桶取；阅读器每次请求都渲染，卷文本由浏览器按卷加载

条目页的一次请求

  1. 边缘网络先看缓存。命中就直接返回，通常 0.1 到 0.25 秒。
  2. 未命中，进云函数。云函数先读数据指针（进程内缓存不超过 60 秒），得到当前数据版本。
  3. 指针 → 版本根清单 → 分片 → 条目文件。后三层按内容哈希命名，永久缓存，函数里用进程内缓存即可。
  4. 渲染 HTML，同时生成 title、description、canonical、OpenGraph 和 JSON-LD。渲染本身约 20 ms CPU。
  5. 带上 s-maxage=3600 返回，边缘网络缓存。函数冷启动约 3 到 5 秒，取数约 0.3 到 0.6 秒，这是未命中的主要耗时。

不存在的 id 返回真 404。被合并的条目（带 merged_into）和已升格的草稿 id 用 308 跳到目标条目。旧地址（/book-index?id=、/item/<id>?tab=、/item/<id>/read）在中间件里一步 308 到新地址，查询参数保留。

阅读页的地址

阅读器是独立的一级目录：/read/<id>?kind=collated|fulltext&key=&juan=。说明类 Markdown 页放在 /read/md/<名>，避免和条目 id 同层撞名。

四、数据怎么流

步骤做什么产物
① 三个数据仓book-index（正式）、book-text（整理本、全文）。CI 里浅克隆；草稿仓 book-index-draft 不再参与部署（overview#432）正式仓条目、卷文本
② 打包bundle-data.mjs 只读正式仓（缺了报错），输出目录在 nextjs/ 之外（public/ 里放 14.7 万个文件会让 next start 起不来）条目 JSON、搜索分片、总目和阅读索引、latest.json
③ 写数据桶（两套并行）current 链：增量上传 current/*，全量上传 v/<commit>/search/，最后写 latest.json。h1 链：文件名带内容哈希，h1/entry/<id>.<hash8>.json，加分片清单和版本根清单数据桶 data.kaiyuanguji.com
④ 指针全部对象上传成功之后才写指针。指针里有三仓的 commit、数据打包日期和 webCommitId（这一版数据对应的网站代码）latest.json、staging/latest.json、h1/manifest-root.json

谁从哪里取数

取数方路径
浏览器先拉 latest.json 得到 commit，再取 current/entry/<id>.json?v=<commit> 和 v/<commit>/search/*。测试站根前缀换成 staging/
条目页云函数h1：指针 → 根清单 → 分片 → 条目文件。任一步读不到，回退到 latest.json 和 current/
阅读器整理本和全文按卷取 h1/text/ 下的文件

测试站的所有数据都写在同一个桶的 staging/ 前缀下，绝不碰根前缀的 current/。current/ 是单副本、原地覆盖的，测试站一写，正式站读者在缓存未命中时就会读到没验过的数据。

数据打包的输入缺一个不会报错，只会静默降级（缺正式仓则正式条目全站 404，缺文本仓则整理本页空白）。所以构建里有数量闸：正式条目逐 id 校验，条目文件不少于 10 万，三个仓在定时比对里一个都不能少。

五、缓存与更新

缓存分三层，各管各的：

对象缓存策略怎么保持新鲜
数据指针边缘不缓存、浏览器 30 秒（控制台规则引擎配置）每次发布都清；服务端取指针时带按分钟取整的时间戳
h1 哈希文件永久，文件名即版本内容变了就换名字，旧文件不用清，7 天后按「没被任何根引用」回收
current/ 文件URL 带 ?v=<commit>换版本就换 URL
条目页 HTMLs-maxage=3600。缓存键含查询串，所以中间件把带多余参数的条目页（utm_*、fbclid 等）308 到干净地址，只保留详情组件自己用的参数（tab、juan、page、mode、collection 等）发布时只清改动的条目（item-changes.mjs 算出改动集 → item-revalidate.mjs 调 /internal/revalidate），再预热前 2,000 个热门页

失效不成功最坏的结果是条目页按 1 小时自然过期。全站的页面缓存不做整站清除：整站清除只清得到裸域，清不到 www 的条目页，而且会把几百 MB 的缓存白丢。

核验缓存要带随机串，例如 ?cb=$RANDOM$RANDOM，看 EO-Cache-Status 是不是 MISS。源站写的 max-age 不可信，节点曾把指针缓存了 18 小时。

六、搜索

搜索分两层，读者感觉不到切换。

L1：Meilisearch跑在上海搜索机（2 核 4 GB），域名 api.kaiyuanguji.com，由 EdgeOne 反代。浏览器直接调用，公开只读 key 随前端下发。
L2：浏览器内搜索浏览器 Worker 读 v/<commit>/search/ 分片，用 MiniSearch 本地检索。L1 超时或熔断时兜底，永远与条目同一个数据版本。

Meilisearch 的索引不由网站部署更新。搜索机上的索引器（源码在网站仓 indexer/）每晚 03:50 从美国机接收三仓数据，04:15 重建，重建期间约 6.5 分钟由 L2 兜底。零停机换索引（swap）已经排在计划里。

七、后台接口

公众站没有数据库。需要写入的功能放在边缘函数里，状态存在 EdgeOne 的 KV 中。

接口作用存在哪
/api/feedback读者反馈。公开列表不含联系方式；管理接口需要管理令牌；新反馈推送到站长微信FEEDBACK_KV
/api/track-error前端错误自收，按版本分组。自动化浏览器不上报ERROR_KV
/api/auth/*邀请制邮箱验证码登录，会话是 JWT（cookie 只属于本域名）。角色以成员记录为准，不放进令牌AUTH_KV
/oauth/*给校对平台的登录。变量未配时返回 503无
/api/version线上是哪一版：网站 commit、组件库版本、数据版本、构建时间构建时写入
/internal/revalidate条目页按改动集失效，凭部署时派生的密钥调用无

三个 KV 命名空间正式站和测试站各一套，变量名相同、命名空间不同，代码不用分支。/admin/* 页面返回 200 加 noindex，真正的边界在接口层：缺配置一律返回 503，不放行。

全栈项目的环境变量是构建时烘进产物的，控制台改了变量必须重新部署才生效。构建用白名单环境跑（ops/edgeone-fullstack-build.py），构建后检查产物里没有 CI 密钥。

八、发布与回滚

发布由 .github/workflows/deploy.yml 负责，分四个 job：check（定时触发时比对三仓 HEAD 与正式站指针，全等就整条跳过）、resolve（决定目标、代码版本、数据版本）、build（单测、打包、写数据桶、构建、部署、清缓存）、verify（等 CDN 传播，再跑 e2e）。

测试站
push main或数据仓更新、定时
单测 · 打包写 staging/ 前缀
构建 · 部署kyg-staging
verify e2e契约 + 浏览器
正式站
promote代码要人点；数据自动
按钉住的 commit 重打代码和三仓都不取 HEAD
部署 wwwkyg-ssr-spike
清缓存 · 预热只清改动的条目页
verify www只读，记入发布记录
  • promote 的两种：code+data 用测试站记下的网站 commit 和三仓 commit；data 用正式站现在的网站 commit，只换数据。所以没 promote 的代码不会被数据发布夹带上线。
  • 自动的部分：数据更新或每天北京时间 04:30 的定时触发，测试站 verify 绿之后自动发一次 promote=data。仓库变量 AUTO_PROMOTE_DATA 设成 false 可以关掉。
  • 为什么按 commit 重打：前端的数据根、统计 ID、站点地址是编译进 JS 的，同一份产物两个站没法共用；重打的输入全部钉死，结果可复现。
  • 并发：测试站、正式站各一个队列，互不阻塞。push 触发的运行自成一组、新 push 会取消旧的；定时和手动运行按目标分组、不被取消，并且 push 会让路给正在跑的定时和手动发布。
  • 构建里的闸：单测不过不发；产物里不许有数据；正式站不许有 noindex 和测试站角标；产物文件数不超过 5,000（平台上限 2 万，超了会静默不发布）。

回滚

入口是 Actions 里的 Rollback，默认 dry_run，先出计划再执行，分三段手动跑：start（目标 commit 在测试站重建并验证）→ promote（发正式站）→ check（核对）。每次正式发布都记入发布记录分支，回滚默认退到上一次记录的版本，约 20 分钟。读者正受影响、等不了时，先在 EdgeOne 控制台回退项目止血，同时把 AUTO_PROMOTE_DATA 设成 false，否则每天的定时数据发布会按指针里的代码版本把它冲回去。

数据不回滚：在数据仓 revert 坏提交，走一次正常发布。旧的静态项目保留到 2026-10-26 前后，作为整个新项目出问题时的最后退路。

九、测试与质量闸

一次改动从提交到读者手里，要过五道闸。

闸内容什么时候跑
PR 闸Jest 单测（约 770 个）；Browser smoke（静态构建、起服务、Playwright）；Fullstack（全栈构建、next start、reader／feedback／read-home／contract 用例）。修失败的测试只能改代码，不许放宽断言每个 PR，以及夜间
自动检查无障碍：e2e 里用 axe 扫首页、总目、阅读首页、条目页、阅读页（桌面和手机），只拦严重和关键级。性能门槛：夜间对正式站量首页与条目页 LCP、条目页缓存命中首字节，超标自动开 issue（perf/thresholds.json）。搜索质量：夜间跑搜索用例，只报告不拦发布PR／夜间
测试站闸verify job：contract（纯 HTTP，几秒：头部、308、真 404、sitemap、数据管线）、ui（真实浏览器：条目、检索、阅读器、整理本、反馈）、degradable（可降级依赖，例如搜索 L1，只报告不拦）。合计 50 多个用例每次测试站部署后
人眼闸QA 在测试站按计划逐页测；截图流水线出 1440 宽的整站图集，给用户看大改动上线前
冻结闸测过的 commit 就是上线的 commit，promote 按钉住的版本发每次 promote
上线后闸对 www 跑同一套 verify（只读）；cutover-check；抽检；24 小时观察每次正式发布

另有几个独立工作流：Data quality（只读巡检数据桶：指针 → 根清单 → 全部分片 → 抽样条目逐字节比对 → 引用完整性 → 卷文件是否齐全）、E2E on a live site（手动对任一线上站跑 e2e）、Page screenshots（主要页面一键截图，只发 GET）。

e2e 会打线上站。写操作用例（反馈提交）必须在浏览器里 mock，绝不能提交到 www，因为 www 用的是正式 KV。测试站用独立 KV，可以放心测。断言新版界面行为的用例要加组件库版本门禁，否则先后顺序一错，发布就红。

十、监控

监控分两半。监控代码只在公开仓 open-guji/open-guji-monitor 里维护（公开仓的 Actions 分钟数免费），不用任何密钥；需要令牌的检查放在网站仓里跑。

位置设计频率检查什么
公开仓 A 探测每 5 分钟（自续循环）首页与组件库版本；搜索 L1、L2；数据桶与指针；条目页（含测试站）；边缘函数（只读）；测试站 robots；四个域名证书剩余天数是否大于 14
公开仓 C 冒烟每 6 小时契约 e2e 打正式站；浏览器指标（LCP 等）；24 小时新旧架构对比报告
网站仓私有半边每小时部署停更（测试站 3 小时、正式站 72 小时跟不上 main）；前端错误突增；反馈量；三个数据仓的新鲜度
每次发布的 verify发布后见上一节

告警的做法：连续 2 次失败才开 issue，恢复自动关，持续失败 6 小时提醒一次；一个检查项至多一张 open 单。检查失败不会让 workflow 变红，workflow 红只表示告警链路自己坏了，所以判断「监控还活着」要看距上次运行多久。对正式站的探测只发 GET。

GitHub 对定时任务会降频（09-29 实测：公开仓 31 小时只触发 10 次，设计约 125 次探测），所以 A 探测不靠定时器：一个长任务（一段约 5.5 小时）里每 5 分钟自己调一次探测，到点用 workflow_dispatch 发起下一段，定时器（每 15 分钟）只作兜底，发现没有在跑的段就重新起一段。网站仓里每小时的私有检查仍靠定时器，实际间隔可能是几小时。

排障入口：docs/runbook.md。第一步永远是先看 /api/version，确认线上是哪一版；错误明细在 /admin/errors，按版本分组。

十一、SEO

目标是让每个条目页都能被搜索引擎收录，并且收录到的是这一条的内容，而不是站点首页。

项目做法
首屏 HTML条目页服务端渲染，标题、作者、简介直接在 HTML 里；简介在首屏就是简体，与水合后一致
标题与描述<title> 为「书名 - 开源古籍」。描述优先用数据里的 SEO 描述字段，没有则用模板：朝代、作者、卷数、简介，截 120 字
canonical指向正式 id 的 https://www.kaiyuanguji.com/item/<id>；被合并条目和已升格草稿不出页面，直接 308
结构化数据JSON-LD：作品和版本用 Book，丛编用 Collection，人物用 Person；只写数据里已有的字段
sitemap索引型 sitemap-index.xml，分片按类型切（作品、版本、丛编、人物），每片不超过 5 万条、10 MB；另有一片 nodes-001.xml 列总目和阅读首页的分类节点页；构建时生成成静态文件。条目数低于阈值（10 万）构建直接失败。robots.txt 逐个列出分片
测试站全站 noindex，robots.txt 全禁，页面带「测试站」角标
真 404不存在的条目返回 404 状态码，不返回 200 的空页面

站长平台（Google Search Console、百度搜索资源平台）的验证和 sitemap 提交需要站长本人操作，之后要定期看收录量和抓取错误。

十二、组件库

索引页的 React 组件不在网站仓，在 npm 包 book-index-ui（源码在 open-guji/book-index-manager 的 ui/）：检索页、条目详情、阅读器、反馈表单、繁简转换。网站仓只做数据源与搜索的装配。

  1. 在 ui/ 里改，跑测试，升 package.json 版本，合入 main。
  2. 手动触发 publish-ui.yml，用 npm Trusted Publishing 发布，不存令牌。
  3. 在网站仓升依赖版本（用 npm install 生成，不手改锁文件），断言新行为的 e2e 用版本门禁，与升版本放同一个 PR。
  4. 合入 main，测试站自动部署，verify 绿，再 promote。

先发包、再推升级，顺序反了 verify 必红。繁简转换用 opencc-js，是组件库的必需对等依赖；数据全部按繁体存，界面按读者偏好同步转换。

十三、安全边界

  • 密钥只放两处：GitHub Actions 的 secrets，和 EdgeOne 项目的环境变量。文档、issue、PR、日志里只写变量名，不写值。
  • 公开数据不含私有文本：构建里有闸，公开产物里搜不到私有文本标记；私有文本不上网站。
  • 公开写接口有限流：反馈接口取不到客户端 IP 时跳过限流并记警告，不回落到可伪造的请求头。
  • 管理接口鉴权显式写出：缺配置即 503，不放行；令牌不走查询串。
  • 正式站只读验证：对 www 的自动化访问只发 GET，绝不提交表单。
  • 2026-09-28 做过一次服务端入口的安全审查，已确认的问题在切正式站前修完。

十四、已知限制与下一步

  • 主域名迁到 openguji.com：只迁读者看得见的 www、裸域和测试站，数据和搜索的域名继续用 kaiyuanguji.com；先等备案新增网站批下来。方案见 overview 仓 40 号进度卡。
  • 搜索代理与轻量分片：让搜索请求走同域代理，并把浏览器兜底分片缩小；观察期结束后再上。
  • 全文搜索：目前只搜书名、目录和部分元数据，全文检索的引擎还在评估。
  • 国内数据桶与大陆加速：数据桶现在在新加坡，国内读者主要靠 EdgeOne 缓存；影像上线前要迁国内并换付费套餐，会改变数据链路。
  • 条目页响应未压缩：条目页（约 25 KB）未命中和命中时都不经过站点的 Gzip／Brotli，静态页和预渲染页是压缩的。09-29 试过两种办法都没用：去掉响应头里的 stale-while-revalidate；直接设平台自己看的 Eo-Cdn-Cache-Control（平台认这个头，但仍不压）。暂不处理，成本是每次多传约 19 KB。
  • 私有监控半边的频率：网站仓里每小时的私有检查（部署停更、前端错误、反馈量、数据新鲜度）仍靠被降频的定时器，实际间隔可能是几小时；这几项不急，暂不改。
  • 条目 SEO 描述：长描述还在分批生成，写入数据后条目页会自动用上。
