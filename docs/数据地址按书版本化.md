# 数据地址按书版本化

## 为什么

COS 桶本月 CDN 回源约 49GB。原因：`current/*?v=<cacheKey>` 的 `cacheKey` 是整库一个键，每次数据发布（约每天 7 次）都换，
EdgeOne 缓存键含全部查询串，所以**没改过的书也整体回源**。一次发布往往只改少数几本书，应该只让改了的书失效。

## 做了什么（第一期：阅读文本）

`current/items/<书 ID>/**`（manifest、各版本 index、章正文、对读 char/cord/punct/entity、章字体子集、read-seed 等）的 `?v=`
由全局 `cacheKey` 改为**这本书自己的 `bookVer`**：

- `bookVer = sha256(该书 items/<id>/ 下每个文件的「相对路径＋内容 md5」，按路径排序拼接)` 取前 16 位。
  **由内容算出，不手动递增**（overview#169、#322 的教训：漏递增就是 CDN 吐旧内容）；回滚内容摘要回到旧值，地址天然回到旧地址，不会撞号。
- 没改的书，`bookVer` 在多次发布间不变，地址不变，一直命中 CDN；改了的书（任何一个文件增删改）地址变。
- 其余文件（entry、promotions、meta、catalog、read、search 等非 `items/<书>/` 下的）**仍用全局 `cacheKey`**，行为不变。

### 清单 `current/vers/<书 ID 末 2 位>.json`

```json
{ "version": 1, "books": { "<书ID>": { "v": "<16位摘要>" } } }
```

- 为什么分片而不是设计稿里的单个 `versions.json`：有文本的书数以千计，单文件几百 KB，每个读者首屏都要下；按 ID 末 2 位切（与 promotions 同一套切法）每片只有几百字节。
- 片的内容逐字节确定（键与书排序、无时间戳），内容没变的片在增量同步里自动跳过；书被删光的片自动当孤儿删掉。
- 取片时 `?v=<全局 cacheKey>`：全局键每次发布换一次，所以清单**永远是新的**（不依赖 EdgeOne 认不认 max-age）；片很小，每次发布每片回源一次可忽略。
- `seq`（给人看的递增号）暂不做；缓存键只用 `v`。

### 回退（新旧前端、新旧数据混跑都照常）

清单取不到（404、网络错）、格式不对、书不在清单里 ⇒ 一律回退全局 `cacheKey`。所以：
- 新前端 + 旧数据（没有 `vers/`）：全部走全局键，与改动前一致；
- 旧前端 + 新数据：旧前端一直用全局键，`current/` 文件路径没变，照常读到。
前端对 404 的清单片记 60 秒不重撞。

## 代码位置

| 位置 | 作用 |
|---|---|
| `nextjs/scripts/lib/book-versions.mjs` | 算每本书的版本、切分片（纯函数，有单测） |
| `nextjs/scripts/sync-to-cos.mjs`（Step 2'） | 算完 md5 后生成 `vers/*.json`，作为普通 shared 文件进增量上传；先于 `latest.json` 上传 |
| `nextjs/scripts/lib/data-content-digest.mjs` | `vers/` 不进全局摘要（它由产物算出，不是打包产物） |
| `nextjs/src/lib/book-version.ts` | 前端／服务端共用口径（分片键、路径规则、清单解析）；与脚本侧一致由 `lib/__tests__/book-version.test.ts` 守着 |
| `nextjs/src/lib/server/item-data.ts` | 服务端 `getCurrentJson/Text/TextHead/currentUrl` 对 `items/<书>/…` 用 bookVer；`getBookVersion(id)` 给阅读页种子 |
| `nextjs/src/lib/cos-storage.ts` | 浏览器端：`getTextFile/getTextFileUrl` 与重写的 `getTextManifest/getTextIndex/getChapter`（原先走 book-index-ui 的 BundleStorage，只认一个全局版本号）；`seedBookVersion` |
| `nextjs/src/app/read/[id]/` | 阅读页服务端把 `bookVersion` 随种子交给浏览器（`string`＝这本书的 bookVer，`null`＝服务端查过没有、用全局键，缺＝旧页面、浏览器自己查）；与 head 里 preload 的地址同一个。页面超过 10 分钟不信种子（与 `dataVersion` 同一条规矩） |

## 不在本期

- `items/<书>/lineage_graph.json`、`volume_book_mapping.json`、`contents/` 等经 book-index-ui 的 BundleStorage 读的文件仍用全局键（量小、非阅读主路径；要改需包支持按路径取版本）。
- 非书内的大文件（`promotions.json` 18.9MB、`catalog/`、`read/` 分片、`meta-home/`）仍随全局键换；后续可同样按「目录／分片内容摘要」各自出键。
- 搜索分片 `v/<cacheKey>/search/` 与 `COS_KEEP_VERSIONS`：搜索分片是 PUT 全量上传、不是 CDN 回源，保留份数只影响存储，不影响本次回源流量，**暂不动**（降到 3～4 份前要先确认没有页面还会引用被清掉的旧键）。旧前端 `v/<commit>/` 副本同理，等旧前端全部刷新后另评估。

## 验收

1. 连续两次发布、只改一本书：别的书的 `?v=` 不变，该书变。
   `curl -s "<数据站>/current/vers/<末2位>.json?v=<latest.json 的 cacheKey>"` 看那本书的 `v`。
2. 读未改的书（任何 `current/items/<书>/…?v=<bookVer>`）：`eo-cache-status` 为 HIT；发布日 COS 回源流量对比（目标降到原来的 1/5 以下）。
3. 改过的书读到新内容，旧页面不报错；`dq.yml` 数据质量检查通过。
4. 回滚一次数据：内容回到旧版，`bookVer` 回到旧值，无旧缓存吐新内容。
