# 精校页与待审条目

> 2026-11-28 整理。基准是 guji-manager 的 `doc/数据库/待审条目与裁定事件.md`；本页只讲**网站这一侧**：精校页怎么取数、怎么投票、数据落到哪。冲突以基准页为准。
> 旧说法「整张待审单、rev、批号、出单／换单、人裁事件」都已废弃：现在每格是一条**待审条目**，没有版本批次，投票写成**裁定事件**。对照表见 ai-team `通用/待审与裁定-现行口径.md`。

## 1. 一格是什么

- 一格＝`(书, 册, u)`。`u` 是字格永久编号，只在册内唯一（见 [字格永久编号u](字格永久编号u.md)）；格号 `页:列:格` 只是当前位置，重切后会变，不当键。
- 精校页上每张卡片＝一个**待审条目**（`item_id`＝`pi_` + 12 位十六进制）。条目随时开、改、关；网站不按「第几版单」决定怎么显示。

## 2. 精校页怎么取数

`/proofing/<书>/<册>`（`nextjs/src/app/proofing/[book]/[vol]/`）打开时取该册当前待审：

| 步骤 | 接口 | 说明 |
|---|---|---|
| 取该册待审 | `GET /api/pending?book=&vol=` | 转 Worker `/v1/web/pending-doc`：Worker 按章现拼，每个「open 且未落定」的条目一格，带 `id`／`ver`／`u`，**无 rev、无整张单**；已落定的格（同 `(书, 册, u)` 有算落定的裁定事件）读时就不返回，AI 摘要随格带上 |
| 各册还剩几格 | `GET /api/pending-index?book=` | 转 `/v1/web/pending-live-index`，精校目录、阅读页横幅用 |
| 退路 | 旧整张单（KV `pd:<书>:<册>`） | Worker 读不到、没有该接口时才退回；等 `guji land` 停止导出整张单后删。`?items=0` 强制走旧路，排查用 |

候选字以卡片字段 `cands/1` 为准（序号即名次，前 `top` 个直接显示，其余折进「更多」）；旧候选字段 `alt[]`／`lib`／`ref` 只作过渡。

## 3. 投票怎么记

- `POST /api/cellreview`：键 `cr:i:<书>:<条目 id>:<投票人>`，值带 `item`、`ver`、`u`（以及 `pick_src`／`pick_rank`／`pick_shown`），**不带 rev**；同人同格重投覆盖旧票。提交缺 `item` 不收。
- 登录会员的 `voter` 是 8 位会员号，匿名是 `sha256(aid|ip)` 前 16 位，见 [membership](membership.md)、[提交带会员身份-方案](提交带会员身份-方案.md)。
- 旧 `cr:<rev>:<书>:<格号>:<投票人>` 票已一次性迁到按条目的键，旧键只读保留，GET `?rev=` 即将随之删除。
- 浏览器里「已回应／存疑」只是本机记忆，按条目存，换包不丢；服务端已确认的才算交过。

## 4. 票之后

1. `proofing-sync`（`.github/workflows/proofing-sync.yml`，每天）：把站内票按条目整条并进中心库 `web_inbox`（`kind=cellreview`，按 `(书, 册, u)` 可查）；并按「有 open 条目」的各章，把单格图从 R2 发到 COS `proof/…`、写 `proof/index.json`（各章 open 数，不含 rev）。章列表与单格图登记取自 Worker `/v1/web/pending-chapters`。
2. `guji cellvotes write` / `guji collect`（guji-manager）：票写成**裁定事件**（`channel=web_vote`），落 book-text。来源三字段 `level`／`by`／`channel` 区分人、AI、机器；「AI 判、人点确认」算 human。
3. `guji pending-settle`：格已落定的条目标 `resolved`，库里状态和网站显示一致。

整个过程不需要「换单」：包换了由 `guji land` 对账条目，网站下一次读就是新的。

## 5. 给开发者的几条

- 配条目、配票、配事件一律 `(书, 册, u)`，**不能只按 u**（别的册有同号 u）；册号写法（`01`／`001`／`vol01`）比较前先归一，Worker `normVol`。
- 网站不读 book-text 的 `pending_file`，也不再有章条目里的 `rev` 字段。
- 待审原因码 `pending_reason` 的枚举由 manager `pending_reasons.yaml` 生成 `pendingReasons.ts`，`pending-reasons-check` 工作流盯两边一致。
