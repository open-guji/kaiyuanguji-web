# 生产验收测试

部署后跑一遍，确认功能没坏、数据真的上线了。

## 为什么要有这套

`perf/smoke.ts` 只验证网络层——字节数、404、pageerror。而 2026-09-02～03 那一连串
故障（整理本 tab 整个消失、书目统计显示"0 部书"、书名标题不渲染、数据版本卡在 9 天前）
**HTTP 全是 200、无 JS 报错、字节数正常**，老 smoke 一个都发现不了。

更糟的是 `perf/scenarios.ts` 里写死的 `aTNoXY45BGY3` 早已 404，但因为不断言内容，
这个场景一直"通过"。

所以这套的核心是**断言内容，而不只是断言请求成功**。

## 三层

| 层 | 位置 | 开浏览器 | 耗时 | 阻断发版 | 查什么 |
|---|---|---|---|---|---|
| contract | `contract/` | 否 | ~10s | ✅ | 数据管线、L2 兜底索引 |
| ui | `ui/` | 是 | ~20s | ✅ | 用户实际看到的渲染结果 |
| degradable | `degradable/` | 否 | ~2m | ❌ | 可降级依赖（搜索 L1） |

contract 不开浏览器，是部署后的第一道门禁——它红了就没必要再跑 UI。

**degradable 为什么不阻断**：搜索 L1 (Meilisearch) 跑在一台 2GB 无 swap 的小
机器上，OOM/卡死是常态化风险（2026-09-03 一天内两次：先公网 IP 变更、后进程
卡死）。前端有 L2 兜底，L1 挂了用户照样能搜。若让它阻断发版，每次都亮红灯，
很快就没人认真看红灯了，真正的回归反而被淹没。

**怎么判读**：

| L1 | L2 | ui/search | 含义 |
|---|---|---|---|
| 🔴 | ✅ | ✅ | 走降级路径，用户无感，择机修 |
| 🔴 | 🔴 | — | 搜索真要挂了，紧急 |

## 跑

```bash
npm install
npm run install-browser          # 首次

npm test                         # 门禁层（contract + ui），发版看这个
npm run test:contract            # 只跑契约层（最快反馈，~10s）
npm run test:ui
npm run test:degradable          # 可降级依赖（搜索 L1）
npm run test:all                 # 含 degradable 的全量
npm run report                   # 看 HTML 报告

TARGET=http://localhost:3000 npm test    # 打本地
```

从仓库根目录也可以：`npm run test:e2e` / `test:e2e:contract` / `test:e2e:ui`。

## 断言怎么写才不会天天误报

本站数据每天都变（升格改 ID、新增条目、reindex），把具体数值写死必然很快失效。
`fixtures/anchors.ts` 里按三档处理：

1. **结构性**——只断言"存在且形态对"，不写死数值。最抗漂移，优先用。
2. **量级**——断言落在合理区间（如 works 在 12万–40万）。防的是归零/暴跌这类
   灾难，不追踪日常增长；撞到上界就把上界调大。
3. **精确**——只用于长期稳定的经典条目（史記的作者不会变成别人）。

版本号一律从 `latest.json` 动态取，绝不写死。

## 已知会红的情况

- **Meili L1 故障**：`搜索 L1` 那几条会红。前端有 L2 兜底，所以 `ui/search`
  仍应通过——这个组合正好告诉你"搜索还能用，但走的是降级路径"。
- **未知 section.type**：数据侧加了新类型而前端映射表没跟上时，
  `整理本卷数据结构完好` 会红。这是有意的——上次就是因为静默退化成兜底渲染，
  才让书名标题消失了很久没人发现。

## 加新用例时

优先复用 `fixtures/anchors.ts` 里的锚点，不要在用例里散落硬编码 ID。
新增锚点时在注释里写清楚"为什么选它"和"什么情况下需要更新"。
